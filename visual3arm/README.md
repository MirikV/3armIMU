# visual3arm

3D-визуализатор руки с часами (Samsung Galaxy Watch 6) на Vue 2 + Babylon.js.
Часы шлют rotation vector в MQTT, браузер подписывается на топик и крутит сцену.

```bash
npm install
npm run dev      # http://localhost:5173
npm test         # тесты математики, парсеров и кинематики (node --test)
npm run build
```

По умолчанию включён **симулятор** — сцена шевелится сразу, без часов и брокера.
Переключение на реальные данные: панель «Источник данных» → MQTT. Третий источник —
**Запись (файл)**: ранее записанный поток с часов, см. «Запись и воспроизведение».

## Что именно приходит с часов

`SensorManager` / `TYPE_ROTATION_VECTOR` отдаёт **не** «вектор поворота» в смысле
ось×угол, а компоненты единичного кватерниона:

| индекс | значение |
|---|---|
| `values[0]` | `x · sin(θ/2)` |
| `values[1]` | `y · sin(θ/2)` |
| `values[2]` | `z · sin(θ/2)` |
| `values[3]` | `cos(θ/2)` — есть с API 18; если не прислали, считается как `√(1-x²-y²-z²)` |
| `values[4]` | оценка точности курса, радианы (только у `ROTATION_VECTOR`) |

Кватернион переводит вектор **из системы устройства в мировую**:

- система устройства: `+X` вправо, `+Y` к верху экрана, `+Z` из экрана. Правая тройка.
- мировая система Android — **ENU**: `+X` восток, `+Y` север, `+Z` вверх. Правая тройка.

Позиции в этих данных нет вообще — только ориентация. Поэтому рука в сцене построена
как «плечо закреплено, предплечье повторяет часы» (см. ниже про заделы).

### Перевод в Babylon

Babylon — **левосторонний**, Y вверх. Оси сопоставлены так:
`babylon.x = android.x` (восток), `babylon.y = android.z` (верх), `babylon.z = android.y` (север).
Перестановка Y↔Z имеет определитель −1 и именно она меняет хиральность.

Итог (`src/core/math/frames.js`): `R_babylon = P · R_android · Q`, где `P` — перестановка
осей мира, `Q = diag(1,1,-1)` — переход от осей устройства к осям меша (в левой тройке
«из экрана» это `-Z`). Проверено тестами: относительные повороты сохраняются один в один,
а оси ложатся физически верно.

## Формат MQTT-пакета

Парсер терпимый, подойдёт почти любой разумный вариант:

Топик по умолчанию — `robot/watch/rotation`. Парсер терпимый, подойдёт почти любой
разумный вариант:

```
[0.12, -0.03, 0.71, 0.69]              ← массив
[0.12, -0.03, 0.71, 0.69, 0.087]       ← + точность курса
[t, x, y, z, w, acc]                   ← 6 чисел: первое считается временем
{"x":0.12,"y":-0.03,"z":0.71,"w":0.69,"timestamp":1737000000000}
{"values":[0.12,-0.03,0.71,0.69],"accuracy":0.087}
0.12,-0.03,0.71,0.69                   ← просто числа через запятую
{"ts":1789730075081,"azimuth":-76.91,"pitch":6.83,"roll":8.68}   ← углы Эйлера
```

Если структура глубже — впишите путь в поле «Путь в JSON» (например `data.sensor`).
Метки времени понимаются в наносекундах (`SensorEvent.timestamp`), миллисекундах и секундах.

Панель «Последние пакеты» показывает сырой текст — по ней удобно чинить формат.

### Углы Эйлера вместо кватерниона

Если часы шлют готовые `azimuth` / `pitch` / `roll` (то, что отдаёт
`SensorManager.getOrientation()`), они восстанавливаются в кватернион как
`R = Rz(−azimuth) · Rx(−pitch) · Ry(roll)` — это точное обратное к тому, что приложение
само показывает в строке «Углы Android». Синонимы ключей тоже понимаются:
`yaw`/`heading`/`az`, `elevation`, `bank`. Нужны все три угла — неполный набор считается
битым пакетом, а не ориентацией с нулём вместо пропущенного угла.

Две вещи, о которых стоит знать:

- **Единицы не помечены в пакете.** Android отдаёт радианы, но обвязки почти всегда
  переводят в градусы. Селектор «Единицы углов» умеет `авто` (градусы, если хоть один
  угол вылезает за радианный диапазон: `|azimuth|`, `|roll| > π` или `|pitch| > π/2`),
  либо явные `градусы`/`радианы`. У `авто` есть дыра: часы почти в нуле
  (`azimuth 2°, pitch 1°, roll 0°`) неотличимы от радиан — поэтому единицы лучше задать
  явно. В подсказке под селектором видно, что распознано на последнем пакете.
- **Углы теряют то, чего в них нет.** Нет `values[4]` — значит, нет оценки точности курса
  (в панели она будет пустой), и нет линейного ускорения — режим позиции `accel` на таком
  потоке работать не будет, оставляйте `fixed`. Плюс на `|pitch| = 90°` курс с креном
  вырождаются. Если у прошивки есть выбор — шлите кватернион, он точнее и меньше шумит.

## Брокер

Браузер не умеет «голый» MQTT поверх TCP — нужен **WebSocket**-листенер.
Для mosquitto:

```conf
listener 1883                 # для часов
protocol mqtt

listener 9001                 # для браузера
protocol websockets
allow_anonymous true          # или заведите пользователя
```

В приложении указывается `ws://<хост>:9001` (или `wss://` за TLS-прокси).

Проверить поток можно так:

```bash
mosquitto_sub -h localhost -t 'robot/watch/rotation' -v
mosquitto_pub -h localhost -t 'robot/watch/rotation' -m '[0,0,0,1]'
mosquitto_pub -h localhost -t 'robot/watch/rotation'   -m '{"ts":1789730075081,"azimuth":-76.91,"pitch":6.83,"roll":8.68}'
```

Со стороны часов — см. `docs/watch-publisher.md` (готовый кусок Kotlin для Wear OS).

## Управление

- ЛКМ — вращать камеру, колесо — зум, ПКМ — панорама.
- **Обнулить по текущей позе** — текущая ориентация становится нулём. Курс у часов
  относительный (датчик без магнитометра), поэтому его начало произвольно: вытяните руку
  вперёд и нажмите кнопку — это направление станет нулевым азимутом, и при нулевом азимуте
  стрела робота смотрит вперёд (`base = 0`). Держите руку при этом **горизонтально**:
  полное обнуление гасит и наклон тоже, то есть объявляет текущее возвышение нулевым, а
  от него отсчитывается наклон стрелы. Взяли ноль с приподнятой рукой — вся картинка
  наклона уедет ровно на столько же (в режиме «только курс» возвышение остаётся
  физическим и от позы обнуления не зависит). Ноль сохраняется в localStorage и переживает
  перезагрузку; порядок с «Измерить скруткой» значения не имеет — ноль пересчитывается под
  новую ось сам. Режим «только курс» гасит азимут, наклон остаётся физическим.
  Взят ноль или нет, видно строкой «ноль» в той же панели.
- **Ось предплечья → «Измерить скруткой»** — самая важная кнопка калибровки. Нажмите,
  2–3 секунды покрутите кистью вокруг предплечья, больше ничем не шевеля, и нажмите
  «Готово». Программа найдёт, где у надетых часов «вдоль руки», и запомнит это.
  Пока ось не измерена, конвейер считает, что вдоль руки смотрят «12 часов» циферблата;
  на живой записи это оказалось неверным на 77°, и скрутка кисти уводила основание
  робота на 141° (см. `src/core/math/forearmAxis.js` и `tests/twistLive.test.js`).
  Знак оси по скрутке не определяется в принципе — если основание смотрит ровно в
  противоположную сторону, а возвышение перевёрнуто, нажмите «Развернуть ось».
- **Установка часов на запястье** — три угла ручной доводки поверх измеренной оси.
  Их же потом можно один раз подобрать и забыть, настройки сохраняются в localStorage.
- **Сглаживание** — постоянная времени фильтра, независимая от частоты пакетов.

Настройки (включая логин/пароль брокера) лежат в `localStorage` открытым текстом —
это дев-инструмент, боевые креды туда лучше не вводить.

## Запись и воспроизведение

Симулятор показывает, что конвейер жив, но не показывает, что делает рука конкретного
человека: дрожание, паузы, паразитный увод оси при скрутке кисти, реальную частоту
пакетов. Для этого есть запись.

- **Запись потока** (панель «Источник данных»): «Начать запись» → «Скачать». Пишутся
  **сырые** пакеты, как пришли с брокера, в файл `.ndjson` — одна строка на пакет:

  ```
  {"t":0.000,"topic":"robot/watch/rotation","payload":"{\"q\":[0.1,0,0,0.99]}"}
  ```

  Payload хранится строкой намеренно: запись должна пережить любые будущие правки
  парсера. Построчность — чтобы файл резался `head` и не умирал целиком от одной
  битой строки (битые строки при загрузке считаются и пропускаются).

- **Воспроизведение**: источник «Запись (файл)» → выбрать файл. Пакеты идут через тот
  же `parsePayload()`, что и живой MQTT, — иначе проверялся бы не тот тракт. Доступны
  скорость (×0.1…×4, применяется на лету, позиция не сбрасывается), пауза, перемотка
  по секундам и зацикливание.

Перемотка — скачок состояния: пропущенные пакеты не досылаются очередью. Планировщик
идёт по стенным часам, а не «по одному таймеру на пакет»: в фоновой вкладке таймеры
душатся до 1 Гц, и наивная цепочка растянула бы минутную запись на час.

Код: `src/core/mqtt/recording.js` (формат), `src/core/mqtt/ReplaySource.js` (источник),
тесты — `tests/recording.test.js`, `tests/replay.test.js`.

## Структура

```
src/

    math/      quat.js · frames.js · euler.js · calibration.js · filter.js
               swingTwist.js       развязка «направление оси» и «скрутка вокруг оси»
               aim.js              ориентация → азимут / возвышение / скрутка предплечья
    mqtt/      MqttSource.js · MockSource.js · parsers.js · emitter.js
               recording.js        формат записи пакетов (NDJSON)
               ReplaySource.js     воспроизведение записи как обычный источник
    robot/     RobotModel.js       цепь шарниров + прямая кинематика
               armToRobot.js       стратегии «прицел руки → углы моторов»
               JointLimiter.js     скорость/ускорение приводов (симуляция шаговиков)
    motion/    PositionEstimator.js  задел под координаты
  scene/       SceneManager.js · RobotRig.js · glbBinding.js · primitives.js
  components/  Viewer3D.vue + панели
  store/       состояние: горячий путь мимо реактивности Vue
tests/         node --test, без браузера
```

Поток данных: `MqttSource | MockSource | ReplaySource → parsePayload → Calibration →
QuatSmoother → androidQuatToBabylon` и далее `forearmAim → mapArmToRobot →
live.robotTarget → JointLimiter → RobotModel → RobotRig`.

Горячий путь (50–100 Гц) идёт через **нереактивный** объект `live`, реактивная витрина
`telemetry` обновляется 12 раз в секунду — иначе Vue захлёбывается на каждом пакете.

## Заделы (то, ради чего всё разложено по файлам)

### 1. Перемещение в координатах

`src/core/motion/PositionEstimator.js` — режимы `fixed` (сейчас) и `accel`
(двойное интегрирование с ZUPT). Модуль пока никем не вызывается. Всё, что нужно для
`accel` — начать слать с часов `TYPE_LINEAR_ACCELERATION` в поле `linearAccel`:
парсер его уже разбирает и прокидывает до `PositionEstimator`.

Честно: MEMS-акселерометр часов уводит позицию на метры за секунды. ZUPT это лишь
притормаживает. Для настоящих координат нужен либо второй источник (камера/UWB/метка),
либо ограничение кинематикой руки — под это оставлен хук `PositionEstimator.constrain()`.

Когда позиция появится, у робота станет наблюдаемым вылет — и в `STRATEGIES`
(`armToRobot.js`) добавится стратегия, которая его использует. Модель руки для этого
не нужна: она была вычислена из тех же трёх чисел и лишней информации не несла,
поэтому удалена.

### 2. 3D-модель робота и углы моторов

Геометрия робота описана данными, а не кодом: `DEFAULT_JOINTS` в
`src/core/robot/RobotModel.js` — имя, ось, длина, лимиты, домашний угол, имя узла в GLB.

- **Без модели** робот рисуется примитивами — работает сразу.
- **С моделью**: положите файл в `public/models/robot.glb`, укажите путь в панели «Робот».
  Риг найдёт узлы по `nodeName`, запомнит их позу из файла как нулевую и будет домножать
  на угол шарнира. Ненайденные имена честно выводятся в панель.

Требования к модели: каждый шарнир — отдельный узел/кость, ось вращения совпадает
с `joint.axis` в локальных осях этого узла.

Пересчёт «поза руки → углы моторов» вынесен в `src/core/robot/armToRobot.js`.
Стратегия — чистая функция; своя кинематика добавляется одной записью в `STRATEGIES`,
остальной код не трогается. Коэффициенты передачи по каждому шарниру крутятся в UI.

#### Оси робота и стратегия по умолчанию

Манипулятор **трёхосевой**: `base` (поворот основания, ось Y), `lift` (наклон стрелы
вверх-вниз, ось X), `wristRoll` (вращение головы вокруг своей оси, Y). Три — не
«сколько поместилось», а сколько наблюдаемых величин есть на входе: с одного IMU на
запястье приходит одна ориентация, то есть азимут оси предплечья, её возвышение и
скрутка кисти вокруг неё (`src/core/math/aim.js`), и больше ничего.

Единственная стратегия `direct` раскладывает их один к одному:

- `base` ← азимут предплечья;
- `lift` ← возвышение предплечья один в один: `lift = 90° − возвышение`, потому что
  наклон отсчитывается от вертикали, а возвышение — от горизонта. Опорные позы
  совпадают по построению, а не по подгонке: рука вперёд → стрела вперёд, рука вверх
  → стрела вверх, рука вниз → стрела вниз. Ползунки в панели только подрезают края
  хода и внутри окна ничего не сдвигают. (Раньше здесь стояло линейное растяжение
  «комфортного» хода руки на ход стрелы — оно уводило горизонтальную руку в стрелу,
  задранную на 67°, и физически разворачивалось сверху диапазона; направление стрелы
  теперь пинится прямой кинематикой в `tests/boomAim.test.js`.) Чтобы стрела повторяла
  руку, мачта сделана выше стрелы, а ход наклона расширен до `[0°, 180°]` — иначе
  поза «стрела вниз» просто недостижима, см. `DEFAULT_JOINTS`;
- `wristRoll` ← скрутка кисти; знак инвертируется, потому что скрутка считается в
  правой тройке Android, а мотор крутится в левой тройке Babylon.

Оси развязаны **по построению**: каждый мотор читает своё число, а азимут, возвышение
и скрутка независимы в самом разложении. Прежний симптом «кручу кисть — едет локоть»
шёл от углов Эйлера по мировым осям; в `tests/robot.test.js` он зафиксирован
негативным контролем, чтобы регрессионный тест не стал пустым.

Единственная оставшаяся связь геометрическая и неустранимая: у почти вертикального
предплечья азимут вырожден, поэтому основание плавно придерживается (`heldAzimuth`),
и панель честно пишет об этом.

**Вылет** («приблизить/отдалить») с одного IMU не наблюдается ни при каком алгоритме:
перенос руки вперёд без смены ориентации даёт побитно тот же пакет. Поэтому такой оси
у робота нет, а вылет задан геометрией стрелы.

Прицел (азимут / возвышение / скрутка) показывается в панели «Робот» в градусах —
видно живые числа, а не только результат.

#### Реализм приводов

`JointLimiter` держит для каждого шарнира максимальные скорость и ускорение: стратегия
выдаёт **цель**, фактические углы подтягиваются к ней трапецеидальным профилем, поэтому
при резком движении руки робот заметно отстаёт — как железо. Интегрирование идёт в
render loop по реальному `dt` (`actions.stepRobot`), а не на приёме пакета: скорость
мотора не должна зависеть от частоты потока с часов. Ограничение по ускорению строгое
на разгоне; торможение может быть резче (остановиться мотор может всегда).

Обратная связь (публикация углов в топик команд) — `MqttSource.publish()` уже есть,
осталось решить, какой формат ждёт железо.
